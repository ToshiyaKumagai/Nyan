# nyan：電子カルテ導入プロセスを支える Claude プラグインの設計

- 起案：2026-09-24（導入部）。2026-09-27 に Notion の構成を3本の横断DBに合わせて改めた版
- 名前の由来：Jean（bw-company/jean）にちなんで **nyan**
- この文書は donyu-standard の `proposals/` から移した設計書。実体はこのリポジトリのルート

---

## 0. 要旨

- donyu-standard の18件のマイルストーン（受け入れ条件＝最低基準）で、実案件の進捗を**任意のタイミングで**評価し、Notion の導入マイルストーンDB（1案件×1節目＝1ページ）と導入週次レビューDB（1案件×1週＝1ページ）に書き込むプラグインを作る
- 入力は議事録（導入議事録DB。社内の StandUp 等と社外の部会・研修等）を軸に、**タスク表・論点シート・Slack・IT基盤の進捗**も参照する。出力は、マイルストーンページの受け入れ条件・理想状態の表の「状態」「事実（根拠）」と更新履歴、週次レビュー（評価・7領域のサマリー・チェックリスト・懸念点・タスク）、Slack への更新文・事実確認・注意喚起
- **判断できる情報が無いときは判断せず、人に返す**。これを構造として持つ（週次レビューの「AIで判断できないものへのレビュー」、Slack の「事実確認」の塊）
- 評価は起案者の叩き台どおり **🔴 要介入／🟡 要観察／🟢 経過観察** を受け入れ条件の行ごとに付け、節目の総合評価は「🔴 が1つでもあれば要介入」。週次レビューの `評価` もこの3段
- **フロントは書き込みを直接直さず、レビューする。レビューを受けて nyan が直す**（表の「コメント」の列・ページのコメントと `progress --review`）
- スキルは **フロー／プロセス／ツール** の3層。依存はプロセス → フロー・ツールの一方向だけ
- 置き場は別リポジトリ **`ToshiyaKumagai/nyan`**

nyan が最初に担うのは、定義書の一文（`01_core/structure.md`）のうち「**事実で測る**」の部分。事実の記録の型は同 8章が暫定なので、nyan で作りながら詰め、2案件以上で再発したものだけを標準へ戻す（`CLAUDE.md`）。

## 2. なぜ別リポジトリか

1. donyu-standard は「標準だけを持ち、案件データを置かない」（README）。nyan は案件データを読み書きするので、同居させると境界が崩れる
2. 標準の改訂（05 の changelog を伴う PR）とプラグインの改修（プロンプト調整・ツール差し替え）は、変更の頻度も査読の観点も違う
3. プラグインはインストール単位。06 の入力資料まで配布物に混ぜたくない

標準との結び方は 10章（写しをスクリプトで取り込み、コミットのハッシュを記録する）。

## 3. スキルの3層

| 層 | 何を知っている／何をする | 他の層との関係 | 作るもの |
| --- | --- | --- | --- |
| **フロー** | 導入プロセスそのもの。18件の節目・受け入れ条件・判定の向き・順序依存・契約事務の期限・節目の指し方・未達の受け皿・順序とカードの対応。**ツールを呼ばない** | 誰にも依存しない | `flow-donyu` |
| **プロセス** | 業務の手順。何を読み、どう判断し、判断できないものをどう返し、どこへ書き、誰に何を伝えるか | フローとツールに依存。フローの中身もツールの操作手順も自分では持たない | `progress`、`notify` |
| **ツール** | 外部システムの読み書きの作法。原本DBの ID・スキーマ・書き込みの規律・失敗時の振る舞い。**業務の判断をしない** | 誰にも依存しない | `tool-notion-minutes`、`tool-notion-milestone-db`、`tool-notion-weekly-review`、`tool-project-sources`、`tool-slack-post` |

依存を一方向に固定する理由：標準の改訂はフローの写しだけ、DB の列変更はツールだけ、評価の方法の変更はプロセスだけを直せば済む。

### 命名と呼び出し

- プラグイン名 `nyan`。スキルは `skills/<name>/SKILL.md` に平置き（層は接頭で示す。`flow-`／プロセスは接頭なし／`tool-`）。サブフォルダは探索の確認が取れていないので使わない（付録 B）
- 利用者が呼ぶのはプロセスだけ：`/nyan:progress`、`/nyan:notify`。どちらも外部に書くので `disable-model-invocation: true`（明示的に呼ばれたときだけ動く）
- フローとツールは `user-invocable: false`。プロセスから参照されて読み込まれるだけ

## 6. 入力（何を読むか）

| 入力 | 何が分かるか | 所在 |
| --- | --- | --- |
| 導入議事録DB | 決定・宿題・日程・懸念。**軸になる入力**。区分＝社内（StandUp 等）と社外（部会・研修・医事課定例 等）の両方を読む | 原本DB（案件ページの ID で絞る） |
| 導入マイルストーンDB | 前回の断面・人のコメント | 原本DB |
| 導入週次レビューDB | 前回のレビュー（範囲の起点・前週の論点） | 原本DB |
| タスク表 | 各タスクの担当・期限・状態。**現状の確認と、議事録で動いたのに更新されていないタスクの検出、次にやるべきタスクの提示**に使う | 案件ページのプロパティ・本文のリンクか引数 |
| 論点シート | 未決の論点・決める場・期限 | 同上 |
| Slack | 病院とのやり取り・現地の温度感・議事録に載らない決定 | 案件ページのプロパティのチャンネル |
| IT基盤の進捗 | 機器・ネットワーク・連携の状態 | 案件ページのプロパティ・本文のリンクか引数 |

- タスク表・論点シート・IT基盤・Slack の所在は **nyan のリポジトリに書かない**（案件ごとに変わる）。`tool-project-sources` は「渡された所在をどう読むか」だけを持つ
- 入力が無い・読めないときは、その入力に依る行を**未確認**にし、週次レビューの「根拠にした議事録」に読めなかったことを残す

## 7. 出力（どこに何を書くか）

### 導入マイルストーンDB（1案件×1節目＝1ページ）

- 行は標準の18件。タイトルは標準の呼称、`順序`（1〜18）が標準カードを引く鍵（対応表は `flow-donyu`）。案件固有の節目は小数の順序で挟む
- プロパティ：Status・予定時期・ギャップ・打ち手（1〜2文の要約）・AI処理日時・週次レビュー（双方向リレーション）・評価の推移（ロールアップ）
- 本文：判定の基準の引用行 → 受け入れ条件の表（カテゴリ｜主語｜受け入れ条件｜期限（逆算の観点）｜状態｜事実（根拠）｜コメント）→ 理想状態の表（カテゴリ｜主語｜理想状態｜事実（根拠）｜コメント）→ 更新履歴
- 表の行はカードから写す。nyan が書き換えるのは「状態」「事実（根拠）」の列だけ。「コメント」は人の欄。更新履歴は追記のみ
- 評価・ギャップの説明・事実確認・タスクはこのページに書かない

### 導入週次レビューDB（1案件×1週＝1ページ）

- タイトル「<直近のマイルストーン>まであと<N>日」、レビュー日（金曜）、評価（🔴 要介入／🟡 要観察／🟢 経過観察）、要注意ポイント、対象マイルストーン、AI処理日時（必須。子ページのビューはこの値で絞る）
- 本文：直近のマイルストーンの callout → 7領域のサマリー → 今のマイルストーンに対するチェックリスト（未達成項目／AIで判断できないもの）→ 全体を通しての懸念点 → 根拠にした議事録
- 人は書き換えない。StandUp で議論した内容は議事録に残し、nyan が結論として反映する

本文の型の詳細は各ツールのスキルが持つ。

## 8. スキル1：`progress`

### 何をするか

案件ページを1本渡すと、6章の入力を前回のレビュー以降の分だけ読み、18の節目それぞれについて **受け入れ条件の状態 → 信号 → 総合評価** を出し、マイルストーンページに状態と事実を書き、その週の週次レビューを1行作る。

### 手順

1. **範囲を決める。** 直近の週次レビューのレビュー日以降を対象にする。`--since` があればそれを優先。レビューが無ければ全件
2. **入力を読む**（`tool-notion-minutes`・`tool-project-sources`）。議事録は本文を読む（AIサマリは代わりにしない）。読めなかった入力は記録して先へ進む
3. **節目に当てる**（`flow-donyu`）。各事実を、どの節目のどの受け入れ条件の根拠になるかで仕分ける。当てはまらない事実は週次レビューの懸念点か領域のサマリーに残す（捨てない）
4. **行ごとに状態と信号を付ける。** 状態は ○／×／未確認／特定不能／対象外（ページには ○／×／未確認／対象外 で書く）。信号は下の表でページには書かない。**根拠 URL を付けられない○×は付けない**
5. **総合評価を出す。** 下の表
6. **タスクを確かめる。** 節目ごとに、(a) タスク表で進行中のタスクの現状、(b) 議事録・Slack で完了・変更が読み取れるのにタスク表が更新されていないタスク、(c) 受け入れ条件の未達・未確認から導かれる**次にやるべきタスク**を出し、週次レビューに簡潔に書く。タスク表そのものは**書き換えない**
7. **書く前に見せる。** 節目ごとの変更と週次レビューの下書きを出し、`--dry-run` ならここで止まる
8. **書く**（`tool-notion-milestone-db`・`tool-notion-weekly-review`）
9. **差分を返す**（`notify` の入力）

評価の規約（信号と総合評価の表、チーム外の介入の見分け、週次レビューへの写し方）は `skills/progress/SKILL.md` が正本。変えるときはそこだけを直し、`CHANGELOG.md` に1行残す。

### 判断しないことを構造にする

- 未確認・特定不能・入力どうしの食い違い（例：DB の予定時期と議事録の日程が違う）は、**判断せず**週次レビューの「AIで判断できないものへのレビュー」に置く。1件＝1項目で、理由と StandUp で決めたいこと
- 確認が取れた事実は、次の実行でマイルストーンページの状態・事実に反映し、更新履歴に残す

### レビューの反映（`progress --review`）

- フロントは書き込みを直接直さず、マイルストーンページの表の「コメント」の列に書くか、ページにコメントを付ける（どちらも読む）
- `--review` は、指摘を読み、該当するセルを直し、更新履歴に「指摘 → 対応（日付）」を追記する。同意できないときは理由を書いて残す（黙って無視しない）
- 人が値を直接直していた場合も上書きせず、その値を起点にする

## 9. スキル2：`notify`

`progress` の差分を Slack に1本のメッセージとして、**下書き → 承認 → 投稿**の順で出す。

```
【<医療機関名>】マイルストーン進捗の更新（M/D。根拠：StandUp M/D・M/D、タスク表 M/D 時点）

■ 要介入（🔴）
・<マイルストーン>：<未達の条件>。打ち手の案：…（受け皿：…）→ 議論の場を設ける

■ 要観察（🟡）
・<マイルストーン>：<根拠が無い／曖昧な条件> → 方針を求める

■ 事実確認をお願いしたいこと
・<何を・なぜ・誰に>

■ タスク
・更新されていない：<タスク>（議事録 M/D で完了と読める）
・次にやるべき：<マイルストーン> → <タスク>（目安 M/D まで）

Notion：<その週の週次レビューのページ URL>
```

- 5つの塊は固定。空なら「なし」
- **投稿先はリポジトリに持たない。** 引数で指定されたチャンネル → 無ければ案件ページのプロパティのチャンネルを候補に確認 → 見つからなければ聞く
- 承認なしに投稿しない。投稿後の URL を、対象マイルストーンのページの更新履歴に控える

## 10. フロースキル `flow-donyu` とツールスキル

### `flow-donyu`

- 中身は標準の写し（`references/`）と読み方、順序 ↔ カードの対応表だけ。`scripts/sync-standard.sh` で更新し `VERSION` にコミットを記録。写しは手で直さない
- 持つ読み方：節目の指し方／6列の意味（逆算の観点＝期限、スコープ外＝求めないこと）／判定の向き／受け皿の決め方／注意喚起の出どころ（順序依存・契約事務の期限）

### ツール（5本）

| スキル | 知っていること | しないこと |
| --- | --- | --- |
| `tool-notion-minutes` | 導入議事録DB の ID・スキーマ・会議体の選択肢、プロジェクトと開催日で絞るクエリ、本文の節構成 | 評価・書き込み |
| `tool-notion-milestone-db` | 導入マイルストーンDB の ID・スキーマ、順序でカードを引くこと、本文の型、セルの置き換えと更新履歴の追記の規律、書く前に読む・読み戻す | 評価、行の削除、コメントの列と更新履歴の書き換え |
| `tool-notion-weekly-review` | 導入週次レビューDB の ID・スキーマ、直近のレビューの取り方、タイトルの決め方、本文の型、1週＝1行 | 評価の決め方、過去の週の書き換え |
| `tool-project-sources` | 渡された所在（URL）からタスク表・論点シート・Slack・IT基盤の進捗を読む作法。列名の揺れの扱い | 所在を持つこと、書き込み |
| `tool-slack-post` | 下書き → 承認 → 投稿、チャンネルの検索と確認、URL の返し方 | 文面を考える、承認前の投稿 |

Notion・Slack・Sheets は claude.ai のコネクタを使う。プラグインに `.mcp.json` は置かない。スキーマの変更（列・選択肢の追加）はスキルの仕事ではなく、必要なら提案を返す。

## 11. 実行の形と進め方

- 任意のタイミングで `/nyan:progress <案件ページのURL> [--since] [--dry-run]` → `/nyan:notify [#channel]`。レビューを受けたら `/nyan:progress <URL> --review`
- 慣れたら金曜の StandUp に合わせて金曜朝に `progress` だけ Routine で走らせる。自動投稿は入れない

| 段 | やること | 目安 |
| --- | --- | --- |
| 1 | `ToshiyaKumagai/nyan` を新設し、叩き台を移す | 済み |
| 2 | Notion を3本の横断DBに集約 | 済み（2026-09-27） |
| 3 | タスク表・論点シート・IT基盤の進捗の所在を案件ごとに受け取る | 3つの URL |
| 4 | `progress --dry-run` を最初の案件で1回走らせ、結果を全部読む | 18節目の状態と週次レビューの下書き |
| 5 | 書き込み → フロントのレビュー → `--review` で反映、を1周 | 更新履歴に1組 |
