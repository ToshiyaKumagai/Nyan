## 0. 要旨

- donyu-standard の18件のマイルストーン（受け入れ条件＝最低基準）で、実案件の進捗を**任意のタイミングで**評価し、Notion のマイルストーン DB（1節目＝1ページ）に書き込むプラグインを作る
- 入力は社内議事録（StandUp）を軸に、**タスク表・論点シート・Slack・IT基盤の進捗**も参照する。出力はページ本文（受け入れ条件・理想状態・現状・ギャップと打ち手・事実確認・タスク）と、プロパティ（その要約）、Slack への更新文・事実確認・注意喚起
- **判断できる情報が無いときは判断せず、「事実確認」として人に返す**。これを構造として持つ（ページの節・プロパティ・Slack の塊のすべてに「事実確認」がある）
- 評価は起案者の叩き台どおり **🔴 要介入／🟡 要観察／🟢 経過観察** を受け入れ条件の行ごとに付け、節目の総合評価は「🔴 が1つでもあれば要介入」
- **フロントは書き込みを直接直さず、レビューする。レビューを受けて nyan が直す**（ページの「レビュー」節と `progress --review`）
- スキルは **フロー／プロセス／ツール** の3層。依存はプロセス → フロー・ツールの一方向だけ
- 置き場は別リポジトリ **`ToshiyaKumagai/nyan`**

## 2. なぜ別リポジトリか

1. donyu-standard は「標準だけを持ち、案件データを置かない」（README）。nyan は案件データを読み書きするので、同居させると境界が崩れる
2. 標準の改訂（05 の changelog を伴う PR）とプラグインの改修（プロンプト調整・ツール差し替え）は、変更の頻度も査読の観点も違う
3. プラグインはインストール単位。06 の入力資料まで配布物に混ぜたくない

標準との結び方は 8章（写しをスクリプトで取り込み、コミットのハッシュを記録する）。

## 3. スキルの3層

| 層 | 何を知っている／何をする | 他の層との関係 | ミニマムで作るもの |
| --- | --- | --- | --- |
| **フロー** | 導入プロセスそのもの。18件の節目・受け入れ条件・判定の向き・順序依存・契約事務の期限・呼称の揺れ・未達の受け皿。**ツールを呼ばない** | 誰にも依存しない | `flow-donyu` |
| **プロセス** | 業務の手順。何を読み、どう判断し、判断できないものをどう返し、どこへ書き、誰に何を伝えるか | フローとツールに依存。フローの中身もツールの操作手順も自分では持たない | `progress`、`notify` |
| **ツール** | 外部システムの読み書きの作法。スキーマ・ID の扱い・書き込みの規律・失敗時の振る舞い。**業務の判断をしない** | 誰にも依存しない | `tool-notion-minutes`、`tool-notion-milestone-db`、`tool-project-sources`、`tool-slack-post` |

依存を一方向に固定する理由：標準の改訂はフローの写しだけ、DB の列変更はツールだけ、評価の方法の変更はプロセスだけを直せば済む。

### 命名と呼び出し

- プラグイン名 `nyan`。スキルは `skills/<name>/SKILL.md` に平置き（層は接頭で示す。`flow-`／プロセスは接頭なし／`tool-`）。サブフォルダは探索の確認が取れていないので使わない（付録 B）
- 利用者が呼ぶのはプロセスだけ：`/nyan:progress`、`/nyan:notify`。どちらも外部に書くので `disable-model-invocation: true`（明示的に呼ばれたときだけ動く）
- フローとツールは `user-invocable: false`。プロセスから参照されて読み込まれるだけ

## 5. 入力（何を読むか）

| 入力 | 何が分かるか | 所在 | 状態 |
| --- | --- | --- | --- |
| 社内議事録 DB（StandUp 等） | 決定・宿題・日程・懸念。**軸になる入力** | プロジェクトページのインライン DB「社内の議事録一覧」 | 確認済み（最初の案件） |
| マイルストーン DB | 前回の断面・レビュー | 同ページのインライン DB「マイルストーン進捗」 | 確認済み・6章で改修 |
| タスク表 | 各タスクの担当・期限・状態。**現状の確認と、議事録で動いたのに更新されていないタスクの検出、次にやるべきタスクの提示**に使う | StandUp ページの「タスクの整理（URL）」が指す先 | **所在未確定**（URL とスキーマを教えてほしい） |
| 論点シート | 未決の論点・決める場・期限。決めきれていない運用の確定などの根拠 | 案件ごとのスプレッドシート | **所在未確定** |
| Slack | 病院とのやり取り・現地の温度感・議事録に載らない決定 | 案件のチャンネル | チャンネルは案件ごとに指定（7章） |
| IT基盤の進捗 | 機器・ネットワーク・連携の状態。ハードウェア・ネットワーク／システム連携の行の根拠 | IT基盤チームの管理表（Notion か Sheets） | **所在未確定** |

- 入力の所在は **nyan のリポジトリに書かない**（案件ごとに変わる）。プロジェクトページのプロパティか、`/nyan:progress` の引数で渡す。`tool-project-sources` は「渡された所在をどう読むか」だけを持つ
- 入力が無い・読めないときは、その入力に依る行を**未確認**にし、事実確認へ回す。読めなかったことを更新履歴に残す

## 6. マイルストーン DB（改修済み。最初の案件で 2026-09-24 に実施）

### 設計の原則

- **本体はページ。プロパティは要約。** 受け入れ条件・理想状態・現状・ギャップと打ち手・事実確認・タスク・レビュー・更新履歴はページ本文に持つ。プロパティは一覧で見るための要約と信号だけ
- 行は標準の18件に揃える。案件で開かない節目は Status「対象外」で行を残す（欠番にしない）
- タイトルは**案件の現行の呼称**（リハーサル①・運用検討部会② など。現場が呼ぶ名前）。標準の指し方（`00_format.md` 2章の表）は「標準の節目」に置き、nyan はこの値でカードを引く（2026-09-24 の起案者の指示）

### プロパティ（改修後）

| プロパティ | 型 | 用途 | 改修 |
| --- | --- | --- | --- |
| マイルストーン | タイトル | 案件の現行の呼称（例：リハーサル①） | そのまま（新設5行は呼称を置く） |
| 標準の節目 | テキスト | 標準の指し方（例：初回検証）。nyan がカードを引くキー | 新設 |
| 順序 | 数値 | 標準の並び（1〜18） | 値を差し替え |
| 予定時期 | 日付（範囲可） | 案件の計画日 | そのまま |
| Status | セレクト | 未着手／準備中／進行中／完了／対象外（開催状況） | そのまま |
| 評価 | セレクト | 🔴 要介入／🟡 要観察／🟢 経過観察（総合評価） | 選択肢を差し替え |
| 現状の要約 | テキスト | ページ「現状」の要約（1〜2文） | 新設 |
| ギャップの要約 | テキスト | ページ「ギャップと打ち手」の要約 | 改名 |
| 打ち手の要約 | テキスト | 同上 | 改名 |
| 事実確認 | セレクト | あり／なし。「あり」なら人の確認待ちが残っている | 新設 |
| 最終更新 | 日付 | nyan が書いた日 | 新設 |
| 最終更新の根拠 | テキスト | 読んだ入力の一覧（議事録の開催日・タスク表の版 等） | 新設 |
| 標準の版 | テキスト | 写した donyu-standard のコミット | 新設 |

サンプルの評価・ギャップ・打ち手は消した（標準と対応しない値だったため）。予定時期と Status は残した。

### ページ本文の型（1節目＝1ページ。案件固有のことだけを書く）

```
> 判定の基準：donyu-standard <カードのパス> の受け入れ条件（標準の版はプロパティ）。標準の写しはこのページに置かない

# 現状
  ## 受け入れ条件の状態（最新）  ← カテゴリ｜条件（要約）｜状態｜信号｜根拠｜期限
  ## 総合評価
# ギャップと打ち手
# 事実確認をお願いしたいこと
# タスク                        ← 7章
# 7領域に当てはめられなかった事実
# レビュー                      ← フロントの指摘と nyan の対応（追記のみ）
# 更新履歴                      ← 実行ごとに追記
```

- **受け入れ条件・理想状態の本文はページに写さない**（2026-09-24 の起案者の指示）。標準は nyan が実行時に `flow-donyu` から読み、ページには「受け入れ条件（要約）」の列と、プロパティ「標準の版」だけが残る。標準が改訂されても案件のページが古くならない
- 「現状」「ギャップと打ち手」「事実確認」「タスク」は**最新の断面に置き換える**節。「レビュー」「更新履歴」「当てはめられなかった事実」は**追記のみ**の節
- 18ページとも、この型（空）にした（2026-09-24）。「現状」以降は nyan の初回実行で埋まる

## 7. スキル1：`progress`

### 何をするか

案件のプロジェクトページを1本渡すと、5章の入力を前回の更新以降の分だけ読み、18の節目それぞれについて **受け入れ条件の状態 → 信号 → 総合評価 → ギャップと打ち手 → 事実確認 → タスク** をページに書き、プロパティに要約を入れる。

### 手順

1. **範囲を決める。** マイルストーン DB の「最終更新」以降の議事録・Slack・タスク表の変更を対象にする。`--since` があればそれを優先。初回は全件
2. **入力を読む**（`tool-notion-minutes`・`tool-project-sources`）。議事録は本文を読む（AI サマリは代わりにしない）。読めなかった入力は記録して先へ進む
3. **節目に当てる**（`flow-donyu`）。各事実を、どの節目のどの受け入れ条件の根拠になるかで仕分ける。当てはまらない事実は「7領域に当てはめられなかった事実」に残す（捨てない）
4. **行ごとに状態と信号を付ける。** 状態は ○／×／未確認／特定不能／対象外。信号は下の表。**根拠 URL を付けられない○×は付けない**
5. **総合評価を出す。** 下の表
6. **タスクを確かめる。** 節目ごとに、(a) タスク表で進行中のタスクの現状、(b) 議事録・Slack で完了・変更が読み取れるのにタスク表が更新されていないタスク、(c) 受け入れ条件の未達・未確認から導かれる**次にやるべきタスク**（担当の目安・期限の目安＝逆算の観点）を出す。タスク表そのものは**書き換えない**（提案として出し、更新は人が行う。書き戻すかは後で決める）
7. **書く前に見せる。** 節目ごとの変更（評価の前後・新しい×・事実確認の件数・タスクの指摘）を表で出し、`--dry-run` ならここで止まる
8. **書く**（`tool-notion-milestone-db`）。「現状」「ギャップと打ち手」「事実確認」「タスク」を置き換え、「更新履歴」に追記し、プロパティに要約を入れる
9. **差分を返す**（`notify` の入力）

### 評価の規約（起案者の叩き台。2026-09-24）

行（受け入れ条件）ごとの信号：

| 信号 | 条件 | 対応 |
| --- | --- | --- |
| 🔴 要介入 | 最低基準（受け入れ条件）が未達で、チーム外の介入の判断が必要 | 対応策の打ち手について時間を設けて議論する |
| 🟡 要観察 | 最低基準の達成の根拠が無い、または曖昧（状態が未確認・特定不能、または × だが逆算の観点の期限内） | 要注意対象として報告 |
| 🟢 経過観察 | 最低基準を達成している（○） | 報告のみ |

節目の総合評価：

| 総合評価 | 条件 | 対応 |
| --- | --- | --- |
| 🔴 要介入 | 🔴 の行が1つでもある | 要介入として MTG を設ける。どこに何が介入すべきか、打ち手は何かを nyan が案として書く |
| 🟡 要観察 | 🔴 は無いが 🟡 がある | 🟡 の項目をつぶ立てて報告し、プロジェクトからの方針を求める |
| 🟢 経過観察 | すべて 🟢（対象外を除く） | 報告のみ |

- 「未達でチーム外の介入が必要」の見分け：逆算の観点の期限を過ぎている／未達だと起きることが医療安全・法令・請求に触れる／受け皿（意思決定主体）が経営か病院全体で、現場と社内だけでは決められない。いずれかに当たれば 🔴、当たらなければ 🟡
- 議事録に**無い**ことは × の根拠にしない。無いものは未確認（🟡）として事実確認へ
- 常時 🔴 になる節目が出たら、案件の問題ではなく線の引き方の問題として標準へ戻す候補にする（`00_format.md` 3章）

### 事実確認（判断しないことを構造にする）

- 未確認・特定不能・入力どうしの食い違い（例：DB の予定時期と議事録の日程が違う）は、**判断せず**ページ「事実確認をお願いしたいこと」に置く。1件＝1行で、何を・なぜ・誰に確かめるか（主語が病院なら「フロントが病院に」、ヘンリーなら担当者）
- プロパティ「事実確認」を「あり」にし、`notify` の「事実確認」の塊に載せる
- 確認が取れた事実は、次の実行で「現状」へ移し、事実確認の行を消す（更新履歴に「確認済み」と残す）

### レビューの反映（`progress --review`）

- フロントは書き込みを直接直さず、ページ「レビュー」節に指摘を書くか、ページにコメントを付ける（どちらも読む）
- `--review` は、レビューの指摘を読み、該当する節を直し、「レビュー」節に「指摘 → 対応（日付）」を追記する。指摘に同意できないときは対応欄に理由を書いて残す（黙って無視しない）
- nyan の値を人が直接直していた場合も上書きせず、「レビュー」節に「人が変更：…」と記録してその値を起点にする

## 8. スキル2：`notify`

`progress` の差分を Slack に1本のメッセージとして、**下書き → 承認 → 投稿**の順で出す。

```
【<医療機関名>】マイルストーン進捗の更新（M/D。根拠：StandUp M/D・M/D、タスク表 M/D 時点）

■ 要介入（🔴）
・<節目>（<呼称>）：<未達の条件>。打ち手の案：…（受け皿：…）。→ 議論の場を設ける

■ 要観察（🟡）
・<節目>（<呼称>）：<根拠が無い／曖昧な条件>。→ 方針を求める

■ 事実確認をお願いしたいこと
・<何を・なぜ・誰に>

■ タスク
・更新されていない：<タスク>（議事録 M/D で完了と読める）
・次にやるべき：<節目> → <タスク>（目安 M/D まで）

Notion：<マイルストーン DB の URL>
```

- 5つの塊は固定。空なら「なし」
- **投稿先はリポジトリに持たない。** 引数で指定されたチャンネル → 無ければ医療機関名で案件チャンネルを検索し、候補を示して確認 → 見つからなければ聞く
- 承認なしに投稿しない。投稿後の URL をページ「更新履歴」に控える

## 9. フロースキル `flow-donyu` とツールスキル

### `flow-donyu`

- 中身は標準の写し（`references/`）と読み方だけ。`scripts/sync-standard.sh` で更新し `VERSION` にコミットを記録。手で直さない（このリポジトリで動作確認済み）
- 持つ読み方：節目の指し方と案件の呼称の結び方／6列の意味（逆算の観点＝期限、スコープ外＝求めないこと）／判定の向き／受け皿の決め方／注意喚起の出どころ（順序依存・契約事務の期限）

### ツール（4本）

| スキル | 知っていること | しないこと |
| --- | --- | --- |
| `tool-notion-minutes` | 議事録 DB のスキーマ、プロジェクトページから辿る手順、開催日で絞るクエリ、本文の節構成 | 評価・書き込み |
| `tool-notion-milestone-db` | 6章のスキーマと本文の型。節ごとの「置き換え」と「追記」の規律、書く前に読む、書いた後に読み戻す | 評価、行の削除、追記のみの節の書き換え |

Notion・Slack・Sheets は claude.ai のコネクタを使う。プラグインに `.mcp.json` は置かない。

## 12. GitHub の新設手順（起案者にお願いすること）

Claude のこのセッションは `ToshiyaKumagai/donyu-standard` にしか GitHub の権限が無いため、リポジトリの新設は起案者が行う。
