# 入力を読み、節目に当て、マイルストーンとレビューに書く（プロセス層）

引数：`$ARGUMENTS`（案件ページ＝PTS Project の1ページの URL か ID。子ページの URL なら親の案件ページに辿る）

参照するスキル（中身をここに写さない）：標準の読み方・順序とカードの対応 → `flow-donyu`／議事録 → `tool-notion-minutes`／タスク表・論点シート・Slack・IT基盤 → `tool-project-sources`／マイルストーン → `tool-notion-milestone-db`／週次レビュー → `tool-notion-weekly-review`

## 原則

- **判断できる情報が無ければ判断しない。** 週次レビューの「AIで判断できないものへのレビュー」に置いて人に返す。推定で埋めない
- 根拠 URL を付けられない○×は付けない。入力に**無い**ことは × の根拠にしない（未確認）
- マイルストーンページは本体が表、プロパティは要約。評価・ギャップの説明・事実確認・タスクは週次レビューに書き、マイルストーンページには書かない
- 人の書き込みを上書きしない。表の「コメント」の列は人の欄で触らない。人が値を直していたら、その値を起点にし、更新履歴に「人が変更：…」と残す
- 案件ページの配下に旧DBが残っていたら、読まずに「未移行の案件」として報告して止まる

## 手順

1. **範囲。** 直近の週次レビューのレビュー日以降を対象（`tool-notion-weekly-review` の「読む」）。`--since` があれば優先。レビューが無ければ全件
2. **入力を読む。** 議事録は `tool-notion-minutes` で区分＝社内・社外の両方を、本文で読む（AIサマリで代用しない）。タスク表・論点シート・Slack・IT基盤は `tool-project-sources` で、案件ページか引数の所在から読む。読めなかった入力は記録し、その入力に依る行は未確認にする
3. **節目に当てる。** マイルストーンの各行の `順序` で `flow-donyu` の対応表からカードを引き、事実を受け入れ条件の行に当てる。当たらない事実は週次レビューの「全体を通しての懸念点」か、該当する領域のサマリーへ（捨てない）
4. **行ごとに状態と信号。** 状態：○／×／未確認／特定不能／対象外。信号：下の表。マイルストーンページの「状態」には ○／×／未確認／対象外 だけを書く（特定不能は未確認として書く）。信号はページに書かない
5. **総合評価。** 下の表
6. **タスク。** 節目ごとに (a) タスク表で進行中のタスクの現状、(b) 議事録・Slack で完了・変更が読めるのにタスク表が更新されていないタスク、(c) 未達・未確認から導く次にやるべきタスク（担当の目安・期限の目安＝逆算の観点）。**タスク表は書き換えない**。週次レビューに簡潔に書く（該当するチェックリストの項目の「StandUpで決めたいこと」か、「全体を通しての懸念点」に1行）
7. **書く前に見せる。** 節目ごとの変更（状態の前後・新しい×・未確認の件数・タスクの指摘）と、週次レビューの下書き（タイトル・評価・要注意ポイント・本文）を出す。`--dry-run` ならここで止まる
8. **マイルストーンに書く**（`tool-notion-milestone-db`）。受け入れ条件・理想状態の表の「状態」「事実（根拠）」を置き換え、更新履歴に追記し、プロパティ（Status・予定時期・ギャップ・打ち手・AI処理日時）を入れる。表が空のページは、カードから行を写してから書く
9. **週次レビューを書く**（`tool-notion-weekly-review`）。その週の行が無ければ作り、あれば更新する
10. **差分を返す**（`notify` の入力。要介入／要観察／事実確認／タスク、とその週のレビューの URL）

### 週次レビューへの写し方

- 直近のマイルストーン：予定時期の開始日がレビュー日以降で最も近い行。並行して進行中：Status が進行中・準備中の行。この2種を「対象マイルストーン」に入れる
- 評価：対象マイルストーンの総合評価のうち最も重いもの（🔴 要介入 ＞ 🟡 要観察 ＞ 🟢 経過観察）
- サマリーの7領域の色：その領域の行の信号のうち最も重いもの
- 未達成項目へのレビュー：直近のマイルストーンで状態が×の行。AIで判断できないものへのレビュー：状態が未確認・特定不能の行。入力どうしの食い違い（例：DB の予定時期と議事録の日程が違う）もここに置く
- 全体を通しての懸念点：先の節目の逆算の観点・順序依存・契約事務の期限から、緊急度の高い順
- 根拠にした議事録：手順2で読んだ入力の一覧（読めなかった入力も明記）

### `--review` のとき

1. 各マイルストーンページの表の「コメント」の列と、ページのコメント（`notion-get-comments`）を読む
2. 指摘ごとに該当のセル（状態・事実（根拠））を直す。同意できない指摘は直さず理由を書く
3. 更新履歴に「指摘 → 対応（日付）」を追記する。黙って無視しない
4. StandUp で週次レビューへの結論が出ていれば（議事録に残っている）、その週のレビューの該当項目に結論の行を足す（`tool-notion-weekly-review`）

## 評価の規約（起案者の叩き台。2026-09-24。変えるときはここだけ直し CHANGELOG.md に1行）

行（受け入れ条件）ごとの信号：

| 信号 | 条件 | 対応 |
| --- | --- | --- |
| 🔴 要介入 | 最低基準が未達で、チーム外の介入の判断が必要 | 打ち手について時間を設けて議論する |
| 🟡 要観察 | 達成の根拠が無い／曖昧（未確認・特定不能、または × だが期限内） | 要注意対象として報告 |
| 🟢 経過観察 | 最低基準を達成している（○） | 報告のみ |

「チーム外の介入が必要」の見分け：逆算の観点の期限を過ぎている／未達だと起きることが医療安全・法令・請求に触れる／受け皿が経営か病院全体。いずれかで 🔴、いずれも無ければ 🟡。

節目の総合評価：

| 総合評価 | 条件 | 対応 |
| --- | --- | --- |
| 🔴 要介入 | 🔴 の行が1つでもある | MTG を設ける。どこに何が介入すべきか・打ち手は何かを案として書く |
| 🟡 要観察 | 🔴 は無いが 🟡 がある | 🟡 の項目をつぶ立てて報告し、方針を求める |
| 🟢 経過観察 | すべて 🟢（対象外を除く） | 報告のみ |

その他のプロパティ：Status（未着手／準備中＝最初の期限が来た／進行中＝初回開催／完了＝最終回開催／対象外）、予定時期（入力に**日程の確定**があるときだけ更新。根拠が無ければ空。食い違いは週次レビューの「AIで判断できないものへのレビュー」へ）。

## しないこと

- 推定で○×を埋める／無いことを × にする／理想状態で判定する
- マイルストーンページに評価・ギャップの説明・事実確認・タスクを書く／表の「コメント」の列や更新履歴を書き換える／行を消す
- 過去の週の週次レビューを書き換える
- タスク表・論点シートを書き換える／Slack に投稿する（`notify`）
- 標準の写しを直す／DB のスキーマを変える（必要なら提案を返す）
