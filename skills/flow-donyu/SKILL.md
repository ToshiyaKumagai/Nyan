# 導入の標準プロセスを知る（フロー層）

このスキルは**読むだけ**。Notion も Slack も呼ばない。案件の判断はプロセスのスキルが行う。

## 正本と写し

- 正本は GitHub の donyu-standard。ここにあるのは `references/` への**写し**で、`references/VERSION` に取り込んだコミットが書いてある
- 写しを手で直さない。食い違いを見つけたら donyu-standard に PR を出し、`scripts/sync-standard.sh` で取り込む

## references/ の中身と読む順

| ファイル | 中身 | いつ読む |
| --- | --- | --- |
| `map.md` | フェーズ・18件の一覧・現行の呼称・計画日（N月＝稼働月からの相対） | 最初に。案件の呼称を節目に結ぶとき |
| `naming.md` | 節目の指し方（短い名前の表）。ID（P2-4 等）と指し方の対応 | 節目を文章で指すとき。**出力では指し方の語を使い、ID は使わない** |
| `cards/*.md` | 各節目のカード。H1／なぜ・現行の呼称・計画日／理想状態／受け入れ条件（6列） | 事実を条件に当てるとき。該当の節目だけ開く |
| `judgment.md` | 判定の向き（受け入れ条件がすべて○で達する／未確認は×でない／順序依存／契約事務の期限の3段） | ○×と評価を付けるとき |
| `forums.md` | 意思決定主体と決定の場（経営→オーナー会議／病院全体→電子カルテ委員会／現場→部会／ヘンリー→社内） | 打ち手の受け皿を書くとき |

## カードの6列の読み方

| 列 | 意味 | プロセスでの使い方 |
| --- | --- | --- |
| カテゴリ | 7領域＋推進体制＋会議体の準備 | 事実の領域を揃える |
| 主語 | 病院／ヘンリー／双方 | 事実確認の宛先を決める（病院主語の未確認はフロントが病院に確かめる） |
| 受け入れ条件 | 節目を達したと認めるのに**必達**の状態 | ○／×／未確認／特定不能を付ける対象 |
| スコープ外 | この節目では**求めない**こと | 求めないことを×にしない |
| 未達だと起きること | 未達のときに後の節目で何が壊れるか | ギャップの説明と注意喚起の文に使う |
| 逆算の観点 | いつまでに要るか（当日まで／1か月前まで／稼働前日まで） | 期限が来たかの判断。太字は前倒しが必須 |

- 「対象外（理由）」の行は判定しない
- 理想状態の表は判定に使わない。書くなら「理想に近づいている兆し」として参考欄に留める

## 判定の要点（judgment.md の要約。迷ったら原文）

1. 判定は名称ではなく受け入れ条件で行う。会議が統合・分割・改称されても、条件が満たされていれば通過
2. 受け入れ条件が**すべて**○で達する。1つでも×か未確認があれば達したと認めない
3. 判定の時点はイベント完了時。逆算の観点に期限がある行は、期限が来た時点で先に○×を付けてよい
4. 計画日を過ぎたが条件は満たしている → 軽微。計画日の内だが条件が未達 → 重い
5. 議事録に**無い**ことを×の根拠にしない。無いものは未確認
6. 判定のときに7領域に当てはめられなかった事実を一覧化する（ゼロなら「なし」と書く）

## 注意喚起の出どころ

- 順序依存（`judgment.md` の「崩すと後段に効く順序依存」）
- 契約・事務の期限（同「契約・事務の期限と紐づく節目」。持ち越し不可＝回線変更届 N-1月20日／実質不可＝機器の発注・抽出費用）
- 常時🔴になる節目は案件の問題ではなく線の引き方の問題として扱い、標準へ戻す候補にする
