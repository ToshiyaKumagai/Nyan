# 判定の読み方（donyu-standard からの写し。手で直さない）

## 3. 保守的に書く（最重要）

受け入れ条件に理想を書くと判定が厳しくなり、どの案件も常時赤になって使えなくなる。
**受け入れ条件は「これが無いと次の節目が成り立たない」ものだけに絞り、迷ったら理想状態へ回す。**

### 受け入れの判定

- **受け入れ条件がすべて満たされている** → その節目を**達した**と認める
- 1条件でも未達がある → 達したと認めない。未達の条件を持って、次のどちらかを選ぶ（「未達だと起きること」が判断の材料）
  1. その条件を片付ける（受け皿は、指した観察項目の**意思決定主体**から決まる。経営→オーナー会議／病院全体→電子カルテ委員会／現場→部会／ヘンリー→社内。対応表は `03_catalog/00_format.md` 3章）
  2. 日程を見直す
- 判定の時点は、その節目の**イベント完了時（直後）**。イベントの前に揃うべき条件（逆算の観点に期限があるもの）は、期限が来た時点で先に○×を付けてよい。イベントの中で検証・修正する条件は、イベントが終わった時点で○×を付ける
- イベントの後に初めて得られるもの（稼働後の修正・院内での展開など）は、この節目の判定には使わない。次の節目の受け入れ条件として現れたときに、次の節目の判定で見る

理想状態は判定に使わない。理想状態が空でも未達でも、達したかどうかは変わらない。

**判定のときに、7領域に当てはめられなかった事実**（領域未定・項目未定）を一覧化し、次の節目を危うくしないかを判断する（該当ゼロなら「なし」と記録する）。
これは全節目で同じ手順なので、カードの行としては持たない。

**「全部○で達する」は厳しさの表明ではない。** 受け入れ条件に必達だけを置いてあることの裏返しで、
必達が1つ欠けたまま次へ進むのを許さない、という意味しか持たない。
常時赤になる案件が出たら、それは病院の問題ではなく**線の引き方の問題**として扱う（→「厳しすぎたときの症状と直し方」）。

### 網羅性は落とさない

受け入れ条件は、簡潔さより**網羅性**を優先する。条件は必要なだけ並べてよい（1条件1行で並べる）。
厳しくなる原因は条件の数ではなく、**受け入れ条件と理想状態に振り分けないまま並べること**。
並べた条件は1つずつ「未達だと起きること」で振り分ける。

### 振り分けは「未達だと起きること」で行う

1. 未達のとき、**イベントか後の節目に起きることを具体に書けるか**（何が壊れる・何が成り立たなくなるか） → 書けるなら受け入れ条件
2. 書けない、または暫定手段で当面の業務が回る → 理想状態へ落とすか削る
3. 医療安全・法令・請求に触れるか → 触れるなら、頻度が低くても受け入れ条件（起きることは必ず書ける）

「未達だと起きること」は Pre-mortem（うまくいかなかったと仮定して何が問題だったかを先に書く）の形で埋める。
節目ごとのレビューやワークショップでは、この列を埋める作業がそのまま条件の作り直しになる。

### 理想が混じっているサイン

| サイン | 書き換えの方向 |
| --- | --- |
| 主体性・意欲・納得・自信・手触り・機運といった語が入っている | そのまま理想状態の表へ |
| 「〜が理解している」「〜を認識している」「〜を自覚できている」 | 観測できないので「〜に説明済み」「〜を自ら挙げ、記録に残っている」「〜が一覧化されている」「〜を実行できる」に置き換える |
| 「すべての」「全員が」「漏れなく」「完全に」 | 範囲を絞れないなら理想状態へ。求めない範囲はスコープ外の列に書く |
| 程度を測れない副詞（十分に・スムーズに・きちんと） | 削る。測れる形にできないなら条件にしない |
| 条件を並べたが、「未達だと起きること」が書けていない | 厳しさの原因は条件の数ではなく振り分けの欠落。起きることが書けない条件は理想状態へ落とすか削る |
| **イベントの後に初めて得られるもの**（「稼働後に病院側が自分で設定を直している」「覚えた操作を他の職員に教えている」） | イベント完了時に○×を付けられない。この節目の理想状態へ移すか、それが無いと次の節目が成り立たないなら次の節目の受け入れ条件へ。**イベントの中で検証・修正できること**（「シナリオを通して見つかったずれが記録に残っている」「先行稼働の中で動作が確かめられている」）は受け入れ条件に置いてよい |

### 理想状態に受け入れ条件が混じっているサイン

逆向きの混在も起きる。理想状態の表に次があれば、受け入れ条件へ移すか削る。

| サイン | 書き換えの方向 |
| --- | --- |
| 「〜が揃っている」「〜ができる」「〜が完了している」で、それが無いと初日の業務が止まるもの | 受け入れ条件へ移す（例：端末が確保・設定されている／Henry に安定して接続できる） |
| 「支障が出ていない」「滞りなく進んでいる」「正常に動いている」 | 受け入れ条件の「未達だと起きること」の裏返し。理想を足していないので削る |
| 受け入れ条件と同じ主語・同じ対象で、程度だけが上がっている（「完全に」「すべて」） | 受け入れ条件のスコープ外の列に「〜は求めない」と書けば足りる。理想状態には残さない |

### 見直しの手順は別に持つ

カードを作る・直すときの見直しの手順（どの節をどの順で当て、指摘をどう出すか）は、この規約ではなく
`.claude/skills/milestone-card-review/SKILL.md` が持つ。規約は「何が正しいか」、スキルは「どう見直すか」。
スキルに規約の写しを書かない。見直しで新しい観点が出たら、先にこの規約へ足し、スキルからは参照する。

### 厳しすぎたときの症状と直し方

案件の大半が常時赤になったら、受け入れ条件の書き過ぎを疑う。赤の内訳を見て、
暫定手段で回っているものを理想状態へ移す。定義そのものを緩めるのではなく、
受け入れ条件と理想状態の線を引き直す。

## 1. 判定の向き

1. 判定は名称ではなく受け入れ条件で行う。会議体が統合・分割・改称されても、受け入れ条件が満たされていれば通過と見なす。
2. 計画日・確定日と受け入れ条件の食い違いは、重みが違う。
   - 計画日を過ぎているが受け入れ条件は満たしている → 順序が保てていれば軽微
   - 計画日の内だが受け入れ条件が未達 → 次の節目の前提が崩れるため重い。名称上の会議が終わっていても未達として扱う
3. 受け入れの判定そのもの（受け入れ条件がすべて満たされていること）は `00_format.md` 3章が正本。ここでは繰り返さない。

## 2. 崩すと後段に効く順序依存

- **P0-1 → P1-3**：アセスメントの記録（論点・帳票と情報の依頼・体制・端末と連携・決裁の経路）が無いまま社内キックオフを開くと、聞き直しに時間が消えて部会の構成と依頼の一覧に抜けが出る（2026-09-15 に P0-1 を足し、P1-1〜P1-3 を P1-3 に統合した）
- **P1-3 → P1-4**：部会の一覧とスケジュールが社内で確定し、経営に判断を求める事項の認識が揃っていないと、プレキックオフで経営層に示す提案が無く、費用と体制の判断が持ち帰りになる
- **P1-4 → P2-1**：経営層合意なしの始動宣言は形式化する
- **P2-2 → P2-4／P2-7**：部門の懸念と論点を回収しないまま検討の場を開くと、事実確認に時間が消える（2026-09-15 まで P2-3 が起点だった。P2-3 の退役で P2-2 が受け止める）
- **P2-4・P2-7 → P2-8 → P2-9 → P3-1 → P3-3**：前段未達で次へ進むと、論点が稼働後へ流れ込む
- **P2-10 → P3-2**：現場のレビューが集まる前に病棟の日次フローを確定させると、稼働後に作り直しになる（1週間以上あける）
- **P3-1 → P4-1**：レセプト請求の月次の流れと保留の基準が決まらないまま初回の請求月に入ると、点検が終わらないまま提出期限を迎える
- **P3-5 → P4-1**：稼働月の診療が Henry に記録されていない分は、初回のレセプト請求で出せない（旧システムで請求する分との切り分けが要る）
